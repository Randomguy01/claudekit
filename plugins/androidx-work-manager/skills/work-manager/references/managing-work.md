# Managing Work

## Enqueuing Work

Once you've defined your `Worker` and [your `WorkRequest`](define-work-requests.md), enqueue the work by calling WorkManager's `enqueue()` method, passing the `WorkRequest` you want to run.

```kotlin
val myWork: WorkRequest = // ... OneTime or PeriodicWork
WorkManager.getInstance(requireContext()).enqueue(myWork)
```

Take care when enqueuing work to avoid duplication. For example, an app that uploads its logs every 24 hours might accidentally enqueue the same task many times even though it only needs to run once. Schedule the work as [unique work](#unique-work) to prevent this.

## Unique Work

Unique work guarantees that only one instance of work with a particular *name* exists at a time. Unlike IDs, unique names are human-readable and developer-specified rather than auto-generated by WorkManager. Unlike [tags](define-work-requests.md#tagging-work), a unique name is associated with only a single instance of work.

Apply unique work to both one-time and periodic work. Create a unique work sequence by calling the method that matches the work type:

- [`WorkManager.enqueueUniqueWork()`](../api/androidx.work/work-manager.md) for one-time work
- [`WorkManager.enqueueUniquePeriodicWork()`](../api/androidx.work/work-manager.md) for periodic work

Both methods accept three arguments:

- `uniqueWorkName` — A `String` that uniquely identifies the work request.
- `existingWorkPolicy` — An enum that tells WorkManager what to do if there's already an unfinished chain of work with that name. See [conflict resolution policy](#conflict-resolution-policy).
- `work` — The `WorkRequest` to schedule.

This fixes the duplicate-scheduling issue noted earlier:

```kotlin
val sendLogsWorkRequest =
    PeriodicWorkRequestBuilder<SendLogsWorker>(24, TimeUnit.HOURS)
        .setConstraints(
            Constraints.Builder()
                .setRequiresCharging(true)
                .build()
        )
        .build()

WorkManager.getInstance(this).enqueueUniquePeriodicWork(
    "sendLogs",
    ExistingPeriodicWorkPolicy.KEEP,
    sendLogsWorkRequest
)
```

Now, if the code runs while a `sendLogs` job is already in the queue, the existing job is kept and no new job is added.

Unique work sequences also help when gradually building up a long chain of tasks. For example, a photo-editing app that supports undo could create an `"undo"` chain and append each undo operation in order as needed. See [Chaining work](chaining-work.md) for more details.

### Conflict Resolution Policy

When scheduling unique work, tell WorkManager what action to take on a conflict by passing an enum when enqueuing the work.

For one-time work, provide an [`ExistingWorkPolicy`](../api/androidx.work/existing-work-policy.md), which supports four options:

- `REPLACE` existing work with the new work. This cancels the existing work.
- `KEEP` existing work and ignore the new work.
- `APPEND` the new work to the end of the existing work. This [chains](chaining-work.md) the new work to the existing work, running it after the existing work finishes.

With `APPEND`, the existing work becomes a *prerequisite* to the new work. If the existing work becomes `CANCELLED` or `FAILED`, the new work is also `CANCELLED` or `FAILED`. To run the new work regardless of the status of the existing work, use `APPEND_OR_REPLACE` instead:

- `APPEND_OR_REPLACE` functions like `APPEND`, except that it does not depend on prerequisite work status. If the existing work is `CANCELLED` or `FAILED`, the new work still runs.

For periodic work, provide an [`ExistingPeriodicWorkPolicy`](../api/androidx.work/existing-periodic-work-policy.md), which supports two options, `REPLACE` and `KEEP`. These function the same as their `ExistingWorkPolicy` counterparts.

## Observing Your Work

At any point after enqueuing work, check its status by querying WorkManager by its `name`, `id`, or a `tag` associated with it.

```kotlin
// by id
workManager.getWorkInfoById(syncWorker.id) // ListenableFuture<WorkInfo>

// by name
workManager.getWorkInfosForUniqueWork("sync") // ListenableFuture<List<WorkInfo>>

// by tag
workManager.getWorkInfosByTag("syncTag") // ListenableFuture<List<WorkInfo>>
```

The query returns a [`ListenableFuture`](https://guava.dev/releases/23.1-android/api/docs/com/google/common/util/concurrent/ListenableFuture.html) of a [`WorkInfo`](../api/androidx.work/work-info.md) object, which includes the `id` of the work, its tags, its current [`State`](../api/androidx.work/work-info-state.md), and any output data set using [`Result.success(outputData)`](../api/androidx.work/listenable-worker-result.md).

The [`LiveData`](https://developer.android.com/topic/libraries/architecture/livedata) and [`Flow`](https://developer.android.com/kotlin/flow) variants of each method let you *observe changes to the `WorkInfo`* by registering a listener. For example, to display a message when work finishes successfully:

```kotlin
workManager.getWorkInfoByIdFlow(syncWorker.id)
    .collect { workInfo ->
        if (workInfo?.state == WorkInfo.State.SUCCEEDED) {
            Snackbar.make(requireView(),
                R.string.work_completed, Snackbar.LENGTH_SHORT)
                .show()
        }
    }
```

### Complex Work Queries

**Requires WorkManager 2.4+**

Query enqueued jobs by a combination of tags, states, and unique work names using [`WorkQuery`](../api/androidx.work/work-query.md) objects. This example finds all work with the tag `"syncTag"` that is in the `FAILED` or `CANCELLED` state and has a unique work name of either `"preProcess"` or `"sync"`:

```kotlin
val workQuery = WorkQuery.Builder
    .fromTags(listOf("syncTag"))
    .addStates(listOf(WorkInfo.State.FAILED, WorkInfo.State.CANCELLED))
    .addUniqueWorkNames(listOf("preProcess", "sync"))
    .build()

val workInfos: ListenableFuture<List<WorkInfo>> = workManager.getWorkInfos(workQuery)
```

Each component (tag, state, or name) in a `WorkQuery` is `AND`-ed with the others, and each value within a component is `OR`-ed — for example, `(name1 OR name2 OR ...) AND (tag1 OR tag2 OR ...) AND (state1 OR state2 OR ...)`.

`WorkQuery` also works with the LiveData equivalent, `getWorkInfosLiveData()`, and the Flow equivalent, `getWorkInfosFlow()`.

## Cancelling and Stopping Work

To stop previously enqueued work from running, cancel it by its `name`, `id`, or a `tag` associated with it.

```kotlin
// by id
workManager.cancelWorkById(syncWorker.id)

// by name
workManager.cancelUniqueWork("sync")

// by tag
workManager.cancelAllWorkByTag("syncTag")
```

WorkManager checks the [`State`](../api/androidx.work/work-info-state.md) of the work. If the work is already finished, nothing happens. Otherwise, its state changes to `CANCELLED` and it won't run in the future. Any [`WorkRequest`](../api/androidx.work/work-request.md) jobs [dependent on this work](chaining-work.md) are also `CANCELLED`.

`RUNNING` work receives a call to [`ListenableWorker.onStopped()`](../api/androidx.work/listenable-worker.md). Override this method to handle any cleanup — see [Stop a running Worker](#stop-a-running-worker).

> [!NOTE]
> [`cancelAllWorkByTag(String)`](../api/androidx.work/work-manager.md) cancels *all* work with the given tag.

## Stop a Running Worker

A running `Worker` might be stopped by WorkManager for several reasons:

- You explicitly asked for it to be cancelled (by calling `WorkManager.cancelWorkById(UUID)`, for example).
- For [unique work](#unique-work), you enqueued a new `WorkRequest` with an [`ExistingWorkPolicy`](../api/androidx.work/existing-work-policy.md) of `REPLACE`. The old `WorkRequest` is immediately considered cancelled.
- Your work's constraints are no longer met.
- The system instructed your app to stop the work — this can happen if you exceed the execution deadline of 10 minutes, in which case the work is scheduled for retry later.

Cooperatively abort any work in progress and release any resources your Worker is holding — for example, close open handles to databases and files. Two mechanisms tell you when your Worker is stopping.

### onStopped() Callback

WorkManager invokes [`ListenableWorker.onStopped()`](../api/androidx.work/listenable-worker.md) as soon as your Worker has been stopped. Override this method to close any resources you may be holding.

### isStopped() Property

Call [`ListenableWorker.isStopped()`](../api/androidx.work/listenable-worker.md) to check whether your worker has already been stopped. If you're performing long-running or repetitive operations, check this property frequently and use it as a signal to stop work as soon as possible.

> [!NOTE]
> WorkManager ignores the [`Result`](../api/androidx.work/listenable-worker-result.md) set by a Worker that has received the stop signal, because the Worker is already considered stopped.
